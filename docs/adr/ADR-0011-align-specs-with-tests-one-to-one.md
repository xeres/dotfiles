# ADR-0011 spec とテストを 1:1 で対応させる

## 🤔 背景

本リポジトリは `specs/*.md` に振る舞いの仕様（When / Then 形式）を、`test/**/*.bats` にその検証を置いている。両者の対応が崩れると、spec にあるがテストされていない項目や、テストにあるが仕様の根拠が追えない項目が生じ、どちらが正かが曖昧になる。

実際、mise/uv/python 周りで次のズレが見つかった:

1. `specs/tools.md` の Python セクションは「`UV_PYTHON` が mise の python パスを指す」「`uv` が mise 管理の python 実体を使用する」の 2 つの Then を持つのに、`tools.bats` ではこれらが 1 つの `@test` に同居していた
2. `specs/bootstrap.md` のファイル配置は 7 ファイルを個別の Then として列挙していたが、`bootstrap.bats` では 1 つの `@test` でまとめて検証していた

2 のように管理対象ファイルが増え続ける項目では、spec に列挙を書くと spec とテストの両方を更新し続ける必要があり、追加漏れが起きやすい。

## 💡 決定事項

spec の各 Then と bats の各 `@test` を 1:1 で対応させることを原則とする。

ただし、対象が増え続ける列挙（管理対象 dotfiles の一覧など）については、spec には振る舞いを 1 つの Then として記述し、具体的な対象リストはテストを正（source of truth）とする。CI 検証が困難な項目は spec に「テスト省略」と理由を明記することで、対応の欠落ではないことを示す。

### 決定に至った差別化要素

1 Then = 1 `@test` を保つことで、spec の各主張がどのテストで担保されているかを機械的に追える。レビュー時も「この Then に対応するテストはどれか」を迷わず確認できる。

一方、増え続けるリストまで Then に展開すると、ファイルを 1 つ追加するたびに spec とテストの両方へ行を足す必要が生じ、1:1 を保つための保守コストが線形に増える。そこで「振る舞いは spec、具体リストはテスト」と役割を分け、spec 側を 1 Then に畳む。これにより対象追加時の変更点はテストの 1 箇所に収まり、spec は不変となる。デメリットとして、spec 単体では具体的な対象ファイル名が分からなくなるが、spec からテストを正とする旨を参照させることで補う。

## 🔍 検討した選択肢

|  | 対応の追跡性 | 対象追加時の保守コスト | spec 単体の自己完結性 |
| --- | --- | --- | --- |
| 1 Then = 1 test + 増える列挙はテストを正 | ✅ 機械的に追える | ✅ テスト1箇所のみ | ⚠️ 具体リストはテスト参照 |
| 全項目を Then として列挙 | ✅ 追える | ❌ spec/test 両方を更新 | ✅ spec だけで分かる |
| テストのみ（spec を持たない） | ❌ 仕様根拠が不明 | ✅ テストのみ | ❌ 仕様が存在しない |

### 1️⃣ 全項目を Then として列挙する

管理対象ファイルなどを含め、すべての検証項目を spec の個別 Then として書き出し、対応する `@test` を 1 つずつ用意する。

- ✅ 対応の追跡性: すべて 1:1 で追える
- ❌ 対象追加時の保守コスト: 対象が増えるたびに spec とテストの両方へ追記が必要で、追加漏れが起きやすい
- ✅ spec 単体の自己完結性: spec を読むだけで対象が分かる

### 2️⃣ テストのみを置き spec を持たない

仕様ドキュメントを設けず、bats テストを唯一の正とする。

- ❌ 対応の追跡性: 各テストがどの意図を検証するのかの根拠が残らない
- ✅ 対象追加時の保守コスト: テストだけ直せばよい
- ❌ spec 単体の自己完結性: 仕様が存在しない
